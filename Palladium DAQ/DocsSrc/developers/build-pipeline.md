# Build pipeline

Palladium DAQ is built with the [MATLAB build tool](https://www.mathworks.com/help/matlab/matlab_prog/overview-of-matlab-build-tool.html). The build is defined in `buildfile.m` at the root of the repository, and produces the toolbox installer (`.mltbx`), the HTML documentation, and the standalone application installers.

> **Keep this page up to date.** It describes how the build works today. If you change `buildfile.m`, the tools in `Tools/`, the documentation workflow or the GitHub Actions workflow, update this page in the same change.

## Running the build

Open the MATLAB Project (`PalladiumDAQ.prj`) so that the source folders are on the path, then run tasks from the repository root:

```matlab
buildtool package              % check, test, build the docs, package the toolbox
buildtool doc                  % just the documentation
buildtool test -skip check     % run the unit tests without the code check
buildtool -tasks               % list the tasks 
```

Running a task runs the tasks it depends on first. Tasks with declared inputs and outputs are *incremental*: buildtool skips them when their inputs and outputs are unchanged since their last successful run, and reports them as `Skipped (up-to-date)`. To force one to run again, delete one of its outputs.

## Tasks

| Task | What it does | Depends on |
| --- | --- | --- |
| `check` | Lists code issues in `+Palladium` and `Tests` (`codeIssues`). Reports them but does not fail the build | - |
| `test` | Runs the unit tests in `Tests/Unit Tests`, failing the build if any fail | `check` |
| `apidoc` | Generates the API reference Markdown from the classes' help comments | - |
| `gettingStarted` | Builds the toolbox's Getting Started guide from its Markdown source | - |
| `doc` | Builds the HTML documentation, help index and search database | `apidoc`, `gettingStarted` |
| `package` | Packages the toolbox installer, `Release/Toolbox/PalladiumDAQ.mltbx` | `test`, `doc` |
| `deploy` | Compiles the standalone application and its installers into `Release/Build` and `Release/Package` | `package` |
| `deployDebug` | Compiles a debug build of the standalone application, with a console window, into `Release/Debug Build` | `test` |
| `screenshots` | Retakes the GUI screenshots used in the documentation. Run by hand - see below | - |

The system tests in `Tests/Systems Tests - Simulated Hardware` are not part of the build - run them separately from the Test Browser or with `runtests`.

The hardware tests in `Tests/Connected Hardware` need a real instrument connected, so they are not part of the build or CI either. Each instrument has a folder with a shared abstract base class holding the tests and one small subclass per connection type, e.g. `runtests("Keithley2410_HardwareTest_GPIB")`. The setup the instrument needs (wiring, settings, safety limits) is described at the top of the base class.

## Documentation

### Folders

| Folder | Contents | In git |
| --- | --- | --- |
| `Palladium DAQ/DocsSrc` | Markdown sources: the guide pages, `helptoc.md` (the table of contents), and `GettingStarted.md` | Yes |
| `Palladium DAQ/DocsSrc/reference` | API reference Markdown, generated by `apidoc` | No |
| `Palladium DAQ/DocsSrc/images` | Images used by the pages. `images/gui` holds the GUI screenshots, generated by `screenshots` | Yes |
| `Palladium DAQ/Docs` | Everything generated from DocsSrc: HTML, help index, search database and the Getting Started guide. This is what the toolbox ships | No (only `.gitkeep`) |
| `Tools` | The documentation generators: `GenerateApiReference.m`, `BuildGettingStarted.m`, and the screenshot tool in `DocScreenshots`. Not packaged | Yes |

`Docs` is on the toolbox's MATLAB path, which is how MATLAB finds `info.xml` and lists the documentation in the Help browser. The `.gitkeep` keeps the (otherwise ignored) folder in a fresh clone, since the MATLAB Project puts it on the path.

### apidoc - API reference

`Tools/GenerateApiReference.m` writes one Markdown page per class, plus an index, into `DocsSrc/reference`. It reads MATLAB's class metadata rather than parsing source files:

* Classes, methods, properties and events are described by their help comments - see [Code and comment conventions](code-conventions.md) for how to write them.
* Public and protected members are documented; private and hidden members are left out.
* Properties are grouped into tables: GUI-editable (`SetObservable` with public set access, the same rule the Instrument Options panel uses), public, read-only, constant and protected.
* Instruments are constructed once (with no arguments and no hardware), so that defaults set in their constructor, and the classes and categories of untyped properties, can be shown.
* Methods inherited from documented classes are listed and linked; methods that override a base class method borrow its help if they have none; one-line Categoricals converters get a generated description.
* Documented class names in the Type column link to their pages.

The classes documented are listed in `apidocTask` in `buildfile.m`: some individually, whole namespaces (currently `Palladium.Enums`), and every instrument driver file in `+Palladium/+Instruments` (`FolderClasses`, which reads the folder so that drivers in a user files folder on the path are not picked up). `TestInstrument`, a scratch driver for prototyping, is left out.

### gettingStarted - the toolbox's Getting Started guide

The guide shown from the Add-Ons manager must be a MATLAB script or live script, not HTML. `Tools/BuildGettingStarted.m` builds `Docs/GettingStarted.m` - a live script in MATLAB's plain-text Live Code format - from `DocsSrc/GettingStarted.md`. It fills in `{{version}}` from `Palladium.ver()`, embeds the images (the splash screen and icon) so the guide is self-contained, and turns MATLAB code blocks into runnable code. The syntax it supports is described at the top of `GettingStarted.md`.

The task's inputs include `Palladium.m`, so a version bump rebuilds the guide. Because the guide is generated, it never shows up as a change in git.

### doc - HTML documentation

The pages are converted with [MathWorks DocMaker](https://github.com/mathworks/docmaker) (an add-on, currently version 0.7). DocMaker only builds in place - it writes each HTML page next to its `.md`, and the index and search database next to `helptoc.md` - so `docTask`:

1. Empties `Docs`, keeping only `GettingStarted.m` (built by `gettingStarted`) and `.gitkeep`.
2. Copies the sources - Markdown pages and images - from `DocsSrc` into `Docs`, keeping their folder structure (`GettingStarted.md` is not a DocMaker page and is skipped). It also warns if the GUI screenshots look out of date (see below).
3. Converts each page to HTML with `docconvert`, using the light theme (which suits MATLAB's Help browser). Links to `.md` pages become links to `.html` pages.
4. Runs the MATLAB code blocks in the pages with `docrun`, inserting their output and figures (not in the API reference).
5. Builds `info.xml`, `helptoc.xml` and the search database from `helptoc.md` with `docindex`.
6. Adds a link back to the contents page (`index.html`) at the top of every other page (`AddContentsLinks`). The Help browser shows a contents sidebar, but a web browser - used for the documentation installed with the standalone application - does not. This is done after indexing, so that the link text stays out of the search database.
7. Deletes the Markdown copies.

Points to know:

* **DocMaker converts Markdown using GitHub's Markdown API**, so building the docs needs internet access, and a GitHub token to avoid rate limits. The token needs no permissions. Locally, store it with `setSecret("DocMaker GitHub token")`, or set the environment variable `DOCMAKER_GITHUB_TOKEN`. On GitHub Actions the workflow's own token is used.
* **GitHub's API sometimes times out** (HTTP 502/503/504). Pages are converted one at a time, and a page that times out is retried up to three times.
* **Code blocks are run** by `docrun`. To show a block without running it - for anything needing hardware, launching the GUI, or taking a long time - end the block's last line with a space.
* **DocMaker removes emoji** from the pages, so GUI labels such as **📋 Sequence Editor** appear without their icons.
* **DocMaker 0.7 copies its stylesheets with a read-only attribute**, which would stop the next build overwriting them; the build clears the attribute first. Version 0.8 fixes this.
* **DocMaker must be installed.** Locally, install it from the Add-On Explorer. On GitHub Actions the build installs the pinned release (`docMakerVersion` in `EnsureDocMaker`) itself.

To add a page: write it in `DocsSrc` (or a subfolder), and add it to `helptoc.md`, which also sets its place in the Help browser's contents.

### screenshots - GUI screenshots

The documentation's screenshots of the GUI are taken by a script, so that they can be retaken whenever the GUI changes, all in the same style. `Tools/DocScreenshots/TakeDocScreenshots.m` describes each screenshot as a *scene*: it launches Palladium DAQ with simulated (Debug) instruments, sets the windows up (adding instruments, running a short measurement, opening the Sequence Editor, ...), and saves a screenshot to `DocsSrc/images/gui/<scene>.png`. `CaptureScreenshot.m` does the capturing:

* It exports the window's contents (`exportapp`), and crops to one component of it, found by the component's position - so crops follow any change in layout.
* Screenshots of a whole window get a title bar, as users see it - the window's icon and title, and minimise, maximise and close buttons, in the Windows 11 style. `exportapp` only captures a window's contents, so the title bar is drawn rather than captured: a real one is tinted by the computer's theme and wallpaper, which would make the images differ between computers. Use `TitleBar=false` (or `true`) to override this for a scene.
* It draws outlines and numbered markers on the components to highlight, in the docs' orange. The page text refers to the numbers.
* Images are scaled to 100% if the display is scaled, so they are consistent between computers.
* Keyboard focus is moved to the window itself before each capture, so no text field shows a focus border - otherwise which field has focus varies from run to run.
* A file is only rewritten if the image has changed, so retaking unchanged screenshots doesn't show up in git. Scenes with plots of simulated data allow a small tolerance, since the data differs slightly from run to run.

The scenes run with a screenshot-only config, writing everything to the git-ignored `Tools/DocScreenshots/work` folder, and set the visible folder fields to neutral values such as `C:\Data`, so a developer's own folders never appear in the docs. `TestInstrument`, a scratch instrument for prototyping that isn't shipped, is hidden from the Instruments list.

**The screenshots task needs a display, so it is run by hand, not on GitHub Actions:**

```matlab
buildtool screenshots 
```

Run it after changing the GUI, then review the changed images (git shows which ones) and commit them. The images are committed to git, and the docs build - locally and on CI - uses them as they are. The task also saves a fingerprint of the GUI's source files (`+Views`, `+Components`, `+Sequence/+Views`, the Instrument Controls and `DataViewer.mlapp`) as `images/gui/gui-sources.sha256`. If those files change later, the `doc` task warns that the screenshots may be out of date.

To add a screenshot, add a scene function to `TakeDocScreenshots.m` and its name to `AllScenes`, run the task, and refer to it in a page as `images/gui/<scene>.png` (`../images/gui/<scene>.png` from a subfolder). Scenes take screenshots of the Windows look of the GUI.

### package - the toolbox

`packageTask` builds `Release/Toolbox/PalladiumDAQ.mltbx` from the MATLAB Project's file list, with the version from `Palladium.ver()`. It sets the Getting Started guide to `Docs/GettingStarted.m`, and leaves `DocsSrc` (and any stray Markdown) out, so the toolbox ships only the generated documentation. It also leaves out `TestInstrument.m`, a scratch instrument for prototyping new features, which is not shipped.

## Standalone application

`deploy` compiles `Palladium.m` into a standalone application with MATLAB Compiler. Classes that are only loaded by name at run time - instruments, Instrument Controls, GUI components and views, enumerations and events - are not found by the compiler's dependency analysis, so `AssembleBuildOptions` adds every `.m` file in those folders explicitly (except `TestInstrument.m`). It then builds three installers in `Release/Package`: with the MATLAB Runtime bundled, with a web installer that downloads the Runtime, and with no Runtime. The installers show a summary, a description and installation notes, set in `deployTask`. The notes tell users updating from an earlier version to close Palladium DAQ and uninstall the old version first, because the installer neither replaces files in use nor removes files a new version no longer has (see [Installation](../installation.md)). The installers also install folders that the application reads from disk at run time, rather than from its compiled archive, next to `PalladiumDAQ.exe` in the installation's `application` folder:

* `Docs` - the built HTML documentation, opened by the Help button
* `PalladiumPythonCore` - the Python base class for [Python instruments](../python-instruments.md), which Python imports from there. Only its `.py` files are installed: they are copied into `Release/Build/PalladiumPythonCore` first, leaving out `__pycache__` and any MATLAB autosave files
* `ExamplesAndTemplates/Presets` (`Example.json`), `ExamplesAndTemplates/PythonInstruments` (`TemplatePythonInstrument.py`, the template for new Python instruments) and `Instrument Drivers` (the PPMS's `QDInterface.dll`) - copied into the user files folder on first run, as they are when running in MATLAB (`Controller.Initialise`). The template for new MATLAB instrument drivers is left out: the standalone application can't load MATLAB drivers written after it is built. Both templates are kept out of the Instruments list by `InstrumentController.InstrumentClassesToIgnore`
* `Graphics` - the Palladium icon, which `Controller` passes to the windows as `WindowSettings.PalladiumIconPath`

The presets, Python template and icon are copied into `Release/Build` first, so that only those files are installed; `Docs` and `Instrument Drivers` are installed from the source.

On Windows, the installers also include a private copy of Python, installed as `application/Python`, so that [Python instruments](../python-instruments.md) work with nothing to set up. `PrepareBundledPython` builds it in `Release/Build/Python`:

* It downloads Python's official Windows *embeddable package* - a self-contained Python that needs no installing - for a pinned version (`pythonVersion`), into a cache folder in the system temp folder, and checks it against the SHA-256 that python.org publishes (`pythonSha256`). A cached download is reused if its checksum matches.
* It unpacks it, and adds `Lib\site-packages` to the package's `python3xx._pth` file, which fixes Python's search path.
* It installs the pinned packages (`packages`: pyvisa, pyvisa-py, pyserial and their dependency typing_extensions) into `Lib/site-packages`, using the build computer's Python (the one MATLAB uses, else `python` on the PATH) with `pip install --target`, asking for packages for the bundled version and platform. They are pure Python, so the build computer's Python version doesn't matter, but it needs `pip` and internet access.

To update the bundled Python, choose a version that the minimum MATLAB release supports, and update `pythonVersion` and `pythonSha256` (from the `.spdx.json` file next to the download on python.org). Package versions are pinned with `--no-deps`, so all their dependencies must be listed too.

At startup, `Controller.SetUpPython` chooses which Python to use: `PythonSettings.PythonExecutable` from the config if set, else the bundled one in the standalone application, else whatever MATLAB finds (`pyenv`). `PythonUtils.CheckPythonSetup` then checks it can be loaded and has the required packages; if not, Python instruments are skipped and the user is warned (see [Python instruments](../python-instruments.md)). `Controller.OpenHelp` (the GUI's Help button) opens `Docs/index.html` from the application folder, which is the source root for the toolbox and the `application` folder for an installed application. The documentation is not part of the compiled archive itself. The debug executable (`PalladiumDAQ_Debug.exe`, with a console window showing Palladium DAQ's messages) is a separate standalone build for diagnosing problems, and is not included in the installers.

## GitHub Actions

`.github/workflows/main.yml` runs on pushes and pull requests to `main`, on version tags, and on demand. On an Ubuntu runner it:

1. Starts a virtual display (Xvfb), so `docrun` can capture figures.
2. Installs MATLAB with the Instrument Control Toolbox, and Python 3.13.
3. Runs `buildtool package` - so the code check, unit tests, documentation and toolbox package all run.
4. Uploads the toolbox (`toolbox`) and the built documentation (`docs`) as artifacts.
5. For a version tag (`v*.*.*`), attaches the toolbox to a GitHub release.
